What's actually happening, mapped to Puckette's terms

Block-rate processing
The browser's audio thread calls this processor's process() once per 128-sample render quantum. Everything inside that call is a plain sample-by-sample loop — the same boundary Pd draws between "the scheduler calls a ugen" and "the ugen fills its block."
Control rate vs. audio rate
Frequency and gain are declared a-rate: the browser interpolates them every single sample, so moving the slider glides smoothly with no zipper noise. Feedback and delay time are k-rate: read once at the start of each 128-sample block, then held constant for the whole block — exactly how a control message updates a Pd object between blocks rather than within one.
Delay-free feedback loops
The feedback path reads from a circular buffer at a position that's always at least one block behind the write position. That built-in lag is what makes the cycle computable at all — it's the same reason Pd silently inserts a one-block delay into any patch cord that closes a loop back on itself.
